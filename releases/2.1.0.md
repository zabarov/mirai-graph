# Mirai 2.1.0

Release type: stable production-read software release

## Summary

Mirai 2.1 combines the security-frozen Mirai 2.0 typed Program and governed
Runtime with graph-native source assimilation, components, multidimensional
relation facts, technology compilation, immutable activation plans and
self-describing Project Capsules.

There was no separately published stable `2.0.0` package. The frozen 2.0 core
is the execution foundation of this unified stable release. Valid 1.4 graph
packages and the `mirai-graph` package and CLI aliases remain compatible
throughout 2.x.

## Included

- typed Mirai Program compilation, deterministic pure execution and replay;
- capability-gated repository/Git reads, sandbox patches, allowlisted tests
  and explicit human approvals;
- durable runs, checkpoints, leases, fencing, receipts, recovery,
  compensation, episodes and sanitized evidence;
- proposal-only Files/Git assimilation with provenance and conflict handling;
- graph-native components, contextual operation bindings and
  multidimensional relation facts;
- reviewable technology drafts and deterministic compilation to Mirai Program;
- immutable activation plans with budgets, policy binding, explanations and
  deterministic parallel joins;
- `mirai/` Project Capsule, deterministic lock, generated START, Agent
  Execution Brief and approval-first legacy migration;
- compatibility wrapper package and CLI aliases for `mirai-graph`.

## Release Evidence

- full local `npm run release:check` and packed-artifact audit;
- public Mirai CI and clean-room package installation on Linux, macOS and
  Windows;
- independent Python conformance checker with public cross-platform CI;
- controlled Federation, Larena-shaped and AI Employee pilots without
  production effects;
- owner-authorized isolated AI-assisted security review of exact revision
  `c946d7306099ae03f71cc46f72bcba981e8da03a`, with no unresolved critical or
  high finding;
- public CodeQL at the reviewed revision.

## Authority Boundary

- This is not an external human security audit.
- Stable software release means the contracts and reference implementation are
  installable and production-read eligible; it does not authorize a particular
  deployment.
- Production-write, live network, secret-changing, financial and public
  publishing adapters require separate deployment-specific approval and
  evidence.
- Graph, Program, runtime state, external state, evidence and proposals remain
  separate authority layers.
- Assimilation, learning and migration remain proposal/approval-first.
- Controlled and synthetic pilots do not establish comparative effectiveness,
  model independence or scientific superiority.
